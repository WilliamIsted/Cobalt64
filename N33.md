# Navi 33 (RX 7600 XT) port: stage 1

Branch `navi33-stage1`. Plan and evidence: the `opencore-tahoe-overview` repo,
`RDNA3/Tasks/navi33-cobalt64-port/`.

## What the N33 build does

`make N33=1 MKSDK=... all` builds `Navi48Bringup.kext` with two flags:

- `N33_OBSERVE`: for `1002:7480` only, `probe` accepts the card without the `navi48bringup`
  boot-arg (loading this build by hand is the opt-in) and `start` takes `startN33Observe`
  instead of the Navi 48 ladder. That path maps BAR5, reads `RCC_CONFIG_MEMSIZE` (byte `0x378c`,
  the same on Navi 33), reads the IP discovery binary through `MM_INDEX`/`MM_DATA`, surveys the IPs,
  and installs the TTL hook on Apple's HWServices instance. It arms no interrupts, runs no PSP,
  SMU, GMC or display code, and never publishes `LoadAccelerator`. The only GPU writes are the
  `MM_INDEX`/`MM_INDEX_HI` index registers. `stop` restores Apple's vtable
  (`uninstall_ttl_hook`) and unmaps BAR5.
- `N33_NO_WCOMB`: drops the `ml_io_map_wcomb` call in `DisplayPipeGuard.cpp`'s framebuffer
  benchmark; Sequoia 24H32 does not export it.

Navi 48 behaviour is unchanged in both builds.

## Other changes

- `Navi48AccelPeer.cpp`: `strnstr` replaced by a local bounded search (`n48_contains_n`), in all
  builds. On 24H32 `strnstr` is exported only by `com.apple.kpi.private`, which third-party kexts
  cannot link; `kmutil load` refused the kext over it.
- `AppleTtlHook.cpp`: the vtable guard chooses measured values by kernel major version. Darwin 25
  keeps Tahoe 26.6.2's (`0x570`, `-0xc70`, page offset `0x150`); Darwin 24 uses Sequoia 24H32's
  (`0x570`, `-0xc90`, page offset `0xd40`, from `getTtl` at `0xc2e5d40` in
  `SystemKernelExtensions.kc`). An unknown version refuses, logging the measured values.
- `Info.plist`: `0x74801002` added to the `Navi48Bringup` and `Navi48AppleHWServices`
  personalities only. `Navi48AccelPeer` and `Navi48AppleAccelExperiment` stay Navi 48 only, so
  neither Apple's framebuffer nor its accelerator is offered the card.

## Expected on Navi 33

Apple's HWServices starts on the card and publishes `LoadPlugIn=Load6000`; X6000 HWLibs then
misses `0x7480` in `DeviceCapabilityTbl` and skips all initialisation (overview repo, dispatch
study section 2). Whether HWServices stays registered after that miss decides whether the hook
can install; stage 1 measures it.

## Stage 1 result (2026-10-12, Sequoia 24H32, RX 7600 XT)

Loaded by hand and unloaded with no panic or hang. Discovery parsed unchanged (39 IPs, GC 11.0.2,
DCN 3.2.1). Apple's HWServices attached and published `LoadPlugIn=Load6000`; HWLibs logged
`Unable to find matching firmware device type for device ID: 0x7480` and stayed inert. The hook
verified the 24H32 geometry live (`getTtl` page offset `0xd40`) and installed; `stop` restored
Apple's vtable.

## Stage 2a: guarded runtime access (code only, not yet loaded)

The N33 observe build gains a guarded userspace interface for the stage 2 display experiments.
Nothing runs it at boot and nothing in it drives the GPU on its own; every write is an explicit
`n33ctl` command and is re-checked in the kext.

- `Navi48Bringup::startN33Observe` now also wires the device context for `RREG32`, snapshots the
  GOP scanout (FB base/offset, surface address, pitch, height), and maps BAR0 uncached.
- `Navi48Bringup::n33Call` (user-client selector `0x4e33`) multiplexes: status, list a protected
  range, allowlisted MMIO write, BAR0 read/write/copy/fill. The write allowlist is HUBP0 surface
  address (low/high), surface pitch (value may not change) and flip control (only `UPDATE_LOCK`
  and `FLIP_TYPE`). BAR0 writes are refused below a 16 MiB floor, past the aperture, on any range
  that overflows, and on any range overlapping the GOP scanout or a live DMCUB window (read from
  the hardware each call, so a window DMCUB moves is still covered).
- The legacy user client is admin-only (`clientHasPrivilege`); the observe build refuses the
  native `N48N` client and, when observing, exposes only RegRead, the log calls and `0x4e33`.
- Tool: `tools/n33/n33ctl.c`. Build on the target with
  `clang -O2 -Wall -framework IOKit -framework CoreFoundation n33ctl.c -o n33ctl`; run as root
  after the kext is loaded (`load-n33.sh again`). `n33ctl status` prints the scanout state and the
  protected ranges; `n33ctl flip <bar0off>` points HUBP0 at a VRAM offset.

Bounds checks are overflow-safe (`off > size || len > size - off`), flagged by the automated
security review and fixed before any load.

## Stage 2 step 3: N33 framebuffer (2026-10-12, works with a manual flip)

`N33Framebuffer` (`src/N33Framebuffer.cpp`, pure rules in `amd/n33_fb_pure.h`, slot layout in
`amd/n33_fb_slots.h` generated by `tools/n33/gen_fb_slots.py`) is an `IOFramebuffer` over a VRAM
surface at BAR0 offset `0x2000000` (2560x1440, 32 bpp, 14745600 bytes). `n33ctl fbpublish`
publishes `N33DisplayNub` and the framebuffer after a layout gate checks the 24H32 `IOFramebuffer`
family size (`0x1d0`; ours is `0x218`). The publish writes no register.

- One mode (2560x1440 at 75 Hz, the GOP's), no EDID, no hot-plug, one display.
- As measured, `enableController` and `setDisplayMode` wrote nothing. Scanout moved only with
  `n33ctl flip 0x2000000` (and back with `flip 0x0`), which rewrites the HUBP0 surface address.
- Self-flip (code only, not yet built or loaded): the framebuffer now flips HUBP0 itself. Once
  `enableController` has run and both power attributes are on (`n33fb::scanout_ours`), it asks the
  bringup kext (`n33_fb_scanout`) to point HUBP0 at the surface, and back at the GOP scanout when
  either power attribute goes to 0. The kext re-checks the surface against the live protected ranges,
  writes HIGH then LOW as `n33ctl flip` does, and refuses once `stop` has begun. The framebuffer
  still touches no register itself (pinned in `tests/n33_fb_test.cpp`). With HUBP0 on our surface the
  monitor shows only the N33 display, so make it the main display in System Settings.
  `n33ctl flip` still works and can move HUBP0 behind the framebuffer's back.
- WindowServer enumerates framebuffers once, at its own start: after `fbpublish` it has to be
  restarted (which ends the session) before the display appears.
- `tools/n33/fbopen.c` opens the framebuffer from userspace (`IOServiceOpen` type 0, root) and holds
  it; the connection is exclusive.

Measured on Sequoia 24H32: WindowServer drew a desktop into the surface and two flip runs moved the
monitor to it and back. Host test: `tests/n33_fb_test.cpp`.

## Stage 3 step 1: PSP bootloader chain (2026-10-12, sOS alive)

Plan and evidence: the overview repo, `RDNA3/Tasks/navi33-cobalt64-port/stage3-psp-design.md`.

The N33 observe build lets a user client write two more registers, MP0 `C2PMSG_36` (`0x16064`) and
`C2PMSG_35` (`0x16063`), under the rules in `amd/n33_psp_pure.h`: `C2PMSG_36` only for a whole 1 MiB
window inside BAR0 that passes the existing BAR0 write guard and does not overlap the framebuffer
surface; `C2PMSG_35` only for the four bootloader commands (KDB `0x80000`, SPL `0x10000000`,
SYS_DRV `0x10000`, SOS `0x20000`), with the bootloader idle (`0x80000000`), sOS not alive
(`C2PMSG_81 == 0`) and the validated window still set. Refusal codes 9 to 14 (9 command, 10 window,
11 not ready, 12 no window, 13 sOS alive, 14 window on the framebuffer surface). Every other dword
stays refused.

`n33ctl psp check <psp_13_0_7_sos.bin> [window-offset]` parses and hashes the container and reads the
PSP and MMHUB registers; `n33ctl psp load ...` runs the chain once, with no retries. The file is
`amdgpu/psp_13_0_7_sos.bin` from linux-firmware `afabaf77` (248496 bytes, sha256
`94db505f...a26fa8`); it is not in this repository and the tool refuses any other file. The default
window is VRAM `0x8000000`. The SPL step sends the KDB image, as Linux's `psp_v13_0.c` does.

Result on the RX 7600 XT, Sequoia 24H32: KDB, SPL and SYS_DRV accepted, the sOS came up,
`C2PMSG_58` reads `0x330024` (the container's SOS version) and `C2PMSG_81` is non-zero and rising.
A second `psp load` or `check` sees the live sOS and writes nothing. Host test:
`tests/n33_psp_test.cpp`.

Refusal reasons: IOKit copies no scalar output back on an error return, so in that run `n33ctl`
printed `refused: ok (why 0)` for every refusal. Since then (code only, not yet built) the user client
logs `n33: refused action <a> (why <code>)` for every refused `n33Call`, `n33ctl` points at that log
line, and `n33ctl why <code>` decodes a code without the kext. For `fbpublish` (action 7) the code is
its status, not a write-refusal reason.

## Stage 3 step 1, milestone 2: PSP ring, TMR and GC firmware (code only, not yet built or run)

Design: the overview repo, `RDNA3/Tasks/navi33-cobalt64-port/stage3-psp-m2-design.md`.

The kext owns the PSP kernel-mode ring. Four new `n33Call` actions: 8 ring create, 9 submit one
command, 10 ring destroy, 11 state. The kext builds every ring frame and command itself
(`amd/n33_psp2_pure.h`) in pages userspace cannot write: the ring, command and fence pages at VRAM
`0x8100000` become protected range kind 12 once the ring exists. It accepts only Linux's order:
`LOAD_TOC`, then `LOAD_IP_FW` SMU, then `SETUP_TMR` (VRAM `0x3FC000000`, size = the `LOAD_TOC` answer
rounded up to 4 KiB, at most 32 MiB, clear of the live DMCUB windows), then the 26 GC 11.0.2 / SDMA
6.0.2 images (each once), then `AUTOLOAD_RLC` after RLC_G. VCN, DMUB and every other type are refused.
A timeout or non-zero PSP status latches failure: nothing more is sent, and no BAR0 write is accepted
(the PSP may still be reading), until the kext is reloaded. The ring pages stay protected after a
destroy. `SETUP_TMR` must also end inside MMHUB's `FB_LOCATION_TOP`. `stop()` holds the same lock
across the destroy and the unmap.
`stop()` sends `DESTROY_RINGS` if this load created the ring. `n33Call` is serialized, so no BAR0
write can land while a command is in flight. Refusal codes 15 to 22 (`n33ctl why <code>`).

`n33ctl psp2` (firmware slicing in `tools/n33/n33_fw.h`, as Linux's `amdgpu_ucode_init_single_fw`):

- `psp2 check <fwdir> <smu.bin>`: read-only preflight (PSP and MMHUB registers, the HDP remap
  register, protected ranges against the plan, every firmware file's size and sha256).
- `psp2 2a <fwdir> <smu.bin>`: run the preflight (any refusal stops it), stage the TOC in `fw_pri`,
  create the ring, `LOAD_TOC`. Expected TMR size `0x1300000`; any other answer exits non-zero and
  2b then needs `--size-ok` (up to 32 MiB) or a new placement (above).
- `psp2 2b <smu.bin> --power-cycled [--size-ok]`: SMU image, then `SETUP_TMR`. Once per power cycle.
- `psp2 2c <fwdir>`: stage and load the 26 images, check each lands wholly inside the TMR (as an MC
  address, physical address or TMR offset: the response's form is not documented), `AUTOLOAD_RLC`,
  then poll `RLC_RLCS_BOOTLOAD_STATUS` bit 31 and `CP_STAT` for up to 2 s (Linux reaches its own 100 ms poll at least 79 ms after `AUTOLOAD_RLC` on this card).
- `psp2 state`, `psp2 destroy`.
- `psp2 send <cmd> <type> <off> <size>` and `psp2 ring`: raw calls for `tools/n33/psp2-negative.sh`,
  which runs the commands that must be refused (`pre` before 2a, `post` after it) and checks each
  refusal code in the kernel log. A command the kext accepts is really sent, so they are for that
  script only.

Firmware (not in this repository, pinned by size and sha256 in `n33ctl.c`): `gc_11_0_2_{pfp,me,mec,
rlc,imu,mes_2,mes1}.bin`, `sdma_6_0_2.bin` and `psp_13_0_7_sos.bin` from linux-firmware `afabaf77`;
`smu_13_0_7.bin` 82.95.0 from linux-firmware `217ca6e4`
(`https://gitlab.com/kernel-firmware/linux-firmware/-/raw/217ca6e4/amdgpu/smu_13_0_7.bin`, 287080 bytes,
sha256 `ccecc0fd...231732`; compressed with `zstd -19` it reproduces the `.zst` hash Ubuntu loaded on
this card). Host tests: `tests/n33_psp2_test.cpp`, `tests/n33_fw_test.cpp` (the latter on the real
files: all 26 slice sizes match the design's table).

`fbpublish` now always returns success with its status in `out[0]` (IOKit returns no outputs with an
error), so `n33ctl fbpublish` prints the real status instead of reading a zeroed buffer.

## Stage 3 step 1: the SMU 13.0.7 mailbox, S1 to S3 (code only, not yet built or run)

Design: the overview repo, `RDNA3/Tasks/navi33-cobalt64-port/stage3-smu-handshake-design.md` (D3 to D6).

The kext has three new `n33Call` actions:
- 12 sends one SMU message.
- 13 arms S2 or S3.
- 14 reports the SMU state.

Each message follows Linux's protocol (`smu_cmn.c:311-323`, `:459-530`), under the same lock as every other call:
1. Wait for `C2PMSG_90` to read non-zero.
2. Write `_90` = 0, the argument to `_82` and the index to `_66`.
3. Wait up to 2 s for `_90` to read non-zero.
4. Read the result from `_82`.

The allowlist (`amd/n33_smu_pure.h`):
- **Queries** (S1), argument 0: `GetSmuVersion`, `GetDriverIfVersion`, `GetRunningSmuFeaturesHigh` and `Low`.
- **S2, after arming:**
  - `SetAllowedFeaturesMaskHigh` `0x0001a3a4`
  - `SetAllowedFeaturesMaskLow` `0x71fe7f7f`
  - `EnableAllSmuFeatures`
- **S3:**
  - The kext arms it only after the enable answered `0xFD`.
  - Arming zeroes the 16 KiB driver table page at VRAM `0x8600000` and protects it (kind 13). The page must not overlap a live DMCUB window or any other protected range.
  - Then `SetDriverDramAddrHigh` and `Low` with that page's MC address, and `TransferTableSmu2Dram` `0x1`.
  - The enable may be sent once more, after S3.

Everything else is refused. That includes:
- `Mode1Reset`
- `TransferTableDram2Smu`
- the feature disables
- BACO
- `ArmD3`
- the frequency limits
- the PCIe override
- GFXOFF control

Direct writes to the MP1 mailboxes are refused too, because they are not on the register allowlist. Refusal codes are 23 to 29 (`n33ctl why <code>`).

What a failed message does:
- **A timeout, or a response that is not one of the five codes:** the kext marks PMFW hung, and refuses every later message until it is reloaded.
- **A known non-OK answer to a state-changing message:** it ends the ladder. The exception is `0xFD` from the first enable, which is S3's trigger.
- **`_90` still 0 before sending:** the kext writes nothing and refuses with code 27. The design's pre-wait has no failure path; this one leaves no state behind.
- **Nothing is retried.**

`stop()` sends no SMU message.

The `n33ctl smu` subcommands:
- **`smu check`:** reads the driver, debug and DAL mailboxes. Read-only.
- **`smu s1`:** the four queries. It prints the PMFW version, the interface version and the named feature bits.
- **`smu s2`:** refuses unless both hold:
  - `AUTOLOAD_RLC` was sent and the autoload is still not complete after 2 s.
  - S1 shows `GFX_IMU` or `DPM_GFXCLK` off.

  It then arms, sends the three messages, and polls the autoload again.
- **`smu s3`:** only after an enable answered `0xFD`. It reads the table page back afterwards.
- **`smu enable`:** the re-sent enable.
- **`smu state`.**
- **`smu send <msg> <arg>`:** raw, for `tools/n33/smu-negative.sh` only.

Host test: `tests/n33_smu_test.cpp`.

## Stage 3 step 1: NBIO 4.3, GMC 11 / MMHUB 3.0.2, GFXHUB 3.0 and the GART, G0 to G6 (code only, not yet built or run)

Design: the overview repo, `RDNA3/Tasks/navi33-cobalt64-port/stage3-gmc-design.md` (D1 to D10). G1 to G4 are the
fallback for m2 2a (design Q10); the code supports every step.

The kext has eight new `n33Call` actions:
- 15 `gmc state`: the kext's GMC state. With argument 1 it also takes the G0 snapshot (MMHUB FB location,
  `RCC_CONFIG_MEMSIZE`, the system aperture as found, DCN_VM, HUBP0), which it retakes only while nothing has been
  written in this load. With 0 it reads no register.
- 16 `gmc step N`, N = 1, 2, 3, 4 or 6.
- 17 `gart map`, 18 `gart unmap`, 19 `gart flush`, 20 `gmc restore`.
- 21 a step's plan entry (register, current value, the kext's target) and 22 a journal entry (before, after,
  target), so `n33ctl` can print tables without the kext returning more than a few scalars per call.

Every register value comes from `amd/n33_gmc_pure.h` (`plan()`), computed from the G0 inputs and the fixed
placement: a 256 MiB GART at MC `0x8400000000`, the 512 KiB table at VRAM `0x8800000`, `mem_scratch` at `0x8880000`.
Userspace names a step, a GART slot and a page index or VRAM offset, never a value or an address. The field
shifts and masks are `amd/n33_gmc11_fields.h`, generated from `mmhub_3_0_2_sh_mask.h` and `gc_11_0_0_sh_mask.h`
(not `amdgpu_field_defs.h`, whose `CONTEXTn_CNTL` fields sit one bit higher). The steps:
- **G1:** `0xe4d` = `0x7F000`, `0xe4e` = `0x7F004`, `0xde0` bit 0; then one HDP flush through the remap (BAR5
  dword `0x1FC00`). ASPM is skipped (D9).
- **G2:** allocates the dummy page, fills the table with it (65536 PTEs, flags 0), zeroes `mem_scratch`, and from
  then on protects both (kind 14). Then rows 1 and 2: CONTEXT0 page table base `0x08800001`, start `0x08400000`,
  end `0x0840FFFF`, AGP disabled, the system aperture by D4, the default page `0x8880`, the fault default page.
- **G3:** `MX_L1_TLB_CNTL` and `VM_L2_CNTL` to `CNTL5` (the `CNTL2` invalidate bits are recorded, not compared).
- **G4:** CONTEXT0 live (depth 0), the identity aperture off, contexts 1 to 15 (`0x00555407` under `0x005554FF`,
  retry 0), the 18 invalidation ranges, an HDP flush, the eleven fault defaults, then the engine 17 flush.
- **G6:** the GC versions of G2 to G4, with `CP_DEBUG.CPG_UTCL1_ERROR_HALT_DISABLE` and `CRASH_ON_*` = 0. Refused
  unless `AUTOLOAD_RLC` succeeded in this load (no GC register is read before that) and
  `RLC_RLCS_BOOTLOAD_STATUS` bit 31 is set, and unless the GC FB location equals MMHUB's.

D4: the aperture is `min`/`max` of the one found and Linux's (`0x200000`..`0x20FFBF`), Linux's when the one found is
disabled (LOW > HIGH). It is refused if it would not cover the FB, or would reach the GART (HIGH >= `0x210000`).

Before every step the kext checks:
- the order (G0, then G1 to G4 in turn, G6 after G4);
- the MMHUB FB location, DCN_VM and HUBP0 address and pitch against the G0 snapshot, and DCN's FB base against MMHUB's;
- that the MMHUB fault status reads 0.

So keep HUBP0 still (the N33 display not main) from G0 to the last step.

Each written register is logged and journalled with its before and after values. A read-back mismatch, a fault
status after the step, or a flush that does not complete ends the ladder for this load. `gmc restore` writes every
before-value back, newest first. It is refused once an engine holds a GART address; nothing in this step hands one
out, and stage 3 step 5's first consumer is to set that flag.

The engine 17 flush follows `gmc_v11_0_flush_gpu_tlb` before KIQ/MES. On MMHUB it:
1. takes the semaphore `0x1a6e2`;
2. sends the request `0x00F80001`;
3. waits for the ack;
4. releases the semaphore;
5. sets `MMVM_L2_BANK_SELECT_RESERVED_CID2` bit 25.

On GFXHUB it sends the request and waits for the ack only. The semaphore is read only there, because a read takes it.
A semaphore that never reads 1 sends nothing (Linux carries on).

`gart map` binds the kext's own four host pages (4 KiB, physically contiguous, below 44 bits, filled with a known
pattern) with flags `0x0003000000000077`, or a VRAM range that passes the BAR0 write guard with `0x0003000000000071`.
`gart unmap` puts the dummy page back (flags 0). Both HDP-flush; `gart flush` invalidates the hubs.

At unload (D6) the kext leaves the hubs alone. It points every PTE at the dummy page and flushes each hub that was
given the table. The dummy page is leaked on purpose. The host pages are freed only if every flush acknowledged.

The `n33ctl gmc` subcommands:
- **`gmc state`:** G0, read-only. It prints each step's registers (current, target, "equals" or "differs"), the
  fault, invalidation, NBIF and DCN_VM registers, and the protected ranges, and flags any `0xffffffff`.
- **`gmc g1` to `g4`, `gmc g6`:** one step each. Each prints the plan, the before/after table and the display
  registers (HUBP0, DCN_VM, protected ranges) before and after. G6 also prints `CP_STAT` before and after.
- **`gmc g5`:** the bind test. It maps four host pages at slots 0 to 3, flushes, reads the PTEs back through BAR0,
  unmaps, flushes, and reads them back again. It is not a DMA proof.
- **`gmc restore`.**
- **`gmc flags | step <n> | map | unmap | flush`:** raw, for `tools/n33/gmc-negative.sh`, which has two phases:
  `pre` (fresh load) and `post` (after G2, before G3). The table page is protected only once G2 owns it, so `pre`
  skips the BAR0 writes to it and `post` runs them.

Refusal codes are 30 to 42 (`n33ctl why <code>`).

Host test: `tests/n33_gmc_test.cpp`. Given the Linux tree root it also checks every field, register width and hub
address against the headers.
